# Open Issues, Assumptions and Dependencies

Nothing in this list may be marked compliant until it is resolved and verified. The **Owner**
column says who must act: PhilHealth (PH) or the development team (Dev).

| ID | Topic | Issue / assumption | Owner | Blocks |
|---|---|---|---|---|
| OI-01 | Capacity | **Partly resolved 2026-10-23:** the project owner confirmed that "17 million users" means 17 million client visits to PhilHealth offices per year, not concurrent users. [capacity-plan.md](capacity-plan.md) derives the load (about 68,500 visits a day nationally, 7 tickets a second at the national peak) and proposes SLOs. Still open: replace the peak-factor assumptions with historical counts, agree the SLOs, and run the load test. **No capacity claim is made until then.** | PH | SLOs, sizing, NFR acceptance |
| OI-02 | Infrastructure | The actual server/VM specifications, OS images, network bandwidth and latency per site (Annex B), and whether Docker is permitted, are unknown. A non-Docker install is scripted in `deploy/native` (Ubuntu 24.04 / RHEL 9 family), but has only been checked statically: dry-run, `bash -n`, `systemd-analyze verify`. It has not been run on a real host. | PH | Deployment acceptance |
| OI-03 | Equipment quantities | 122 kiosks/printers/TVs vs 112 servers, and whether "122 rolls" of thermal paper is literal, must be validated against the Bill of Quantities and Annex C. | PH | Procurement |
| OI-04 | Identity | Users are managed locally on each node and are not synchronized. Undecided: central identity (PhilHealth AD/LDAP/SSO), or replicating central-managed users to sites. Until decided, each site needs local admin accounts. | PH + Dev | Single sign-on, central user admin |
| OI-05 | Service catalog | The 29 seeded services follow the specification. Their classification, client type, internal/external type, multi-stage flag, prefixes and durations are **placeholders** and must be validated against the approved Citizen's Charter. | PH | Go-live configuration |
| OI-06 | Priority policy | Seeded categories: Senior, PWD, Pregnant (all rank 10). The legal basis, other authorized categories, verification evidence, and the policy for mixing priority and regular clients (strict priority versus a ratio such as 1:3) must be confirmed. The current policy is strict priority by rank, then FIFO. | PH | Priority acceptance |
| OI-07 | Metric definitions | `metrics-definitions.md` is a draft proposal (queueing vs waiting time, abandonment, rerouting). | PH | Report acceptance |
| OI-08 | Report templates | The official PhilHealth report templates have not been provided. Exports are generic CSV/XLSX; PDF is not implemented. No official template has been invented. | PH → Dev | Reporting compliance |
| OI-09 | Reappointment | "Reappointed" tickets (a client told to return on another date) are not modelled. Only reroutes and transfers are counted. | PH + Dev | Metric completeness |
| OI-10 | CSMST integration | The interface, authentication, data format and credentials of the Client Satisfaction Measurement Survey Tool are unknown. Feedback is captured locally. The integration adapter is not built. | PH | Integration |
| OI-11 | Other integrations | Which other PhilHealth systems must integrate, and through which approved APIs, is not identified. No external system is accessed. | PH | Integration |
| OI-12 | CMS distribution | **Resolved 2026-10-22.** Content published on central (national, regional or site-targeted) reaches sites through the config pull. Media is downloaded with size and SHA-256 verification, and replicas are read-only on sites. Verified by `ContentDistributionIT`; not yet run between two real nodes. | Dev | – |
| OI-13 | Retention and privacy | The retention period for tickets, events, audit logs and feedback is undecided. A Data Privacy Act PIA is pending. The system stores no client names or IDs: priority is self-declared and verified at the counter. The purge job exists (`QMS_RETENTION_*`, see operations.md) but keeps everything until periods are set. | PH | Privacy compliance |
| OI-14 | DB least privilege | **Resolved 2026-10-22.** Migrations run as the schema owner (`SPRING_FLYWAY_USER`). V3 gives the application role DML only, and `audit_log`/`ticket_event` are append-only. Verified by `DatabasePrivilegesIT` and a live two-account start-up. | Dev | – |
| OI-15 | Thermal printing | Kiosk printing uses the browser (Chrome `--kiosk-printing`) with an 80 mm print stylesheet. Direct ESC/POS printing, paper-out detection and printer-status monitoring need a local print agent, which is not built. | Dev + PH (printer models) | Kiosk acceptance |
| OI-16 | Kiosk lock-down | Procedure written ([kiosk-lockdown.md](kiosk-lockdown.md)) for Windows (Shell Launcher + Chrome) and Ubuntu (cage/Openbox + Chromium), but not yet validated on PhilHealth hardware. Edge's built-in kiosk mode probably runs InPrivate and would lose the device key; test before relying on it. | Dev + PH | Kiosk acceptance |
| OI-17 | Audio announcements | The display plays a chime, then speaks "Ticket number A, 0, 0, 4, please proceed to Counter 1." through the browser's speech synthesis (English; Philippine English voice when available). Still to be agreed: a Filipino version, the exact wording, whether to repeat each call twice, and whether recorded human-voice clips are wanted instead of synthesized speech. | PH | Display acceptance |
| OI-18 | Approval workflows | Only CMS content has an approval workflow. "Configurable approval workflows" for other changes (users, catalog) is not implemented. | PH + Dev | Admin requirements |
| OI-19 | Account recovery | Admin password reset is implemented. Self-service recovery (email/OTP) is not, and needs an approved mail gateway. | PH | Account recovery |
| OI-20 | Spring Boot line | Built on Spring Boot 3.5.16, the latest 3.x release available at build time. Confirm the support status of the 3.x line with PhilHealth; migrating to 4.x would be a separate change. | PH + Dev | Maintainability |
| OI-21 | Support terms | The allocation of the 120 man-hours (all sites collectively or otherwise), and the SLA response/restoration targets, are to be set in the approved SLA. | PH | Warranty |
| OI-22 | VAPT | A third-party VAPT by a DICT-qualified provider is required and has not been done. | PH + Dev | Security acceptance |
| OI-23 | Electronic ticketing | Every ticket now has a QR code to a phone page (status, call, feedback). Open: whether clients' phones may reach site servers (guest Wi-Fi or a public address, `QMS_TICKET_LINK_BASE_URL`), and SMS, which needs an approved gateway. | PH | E-ticket scope |
| OI-24 | Accessibility standard | Which accessibility standard applies (for example WCAG 2.1 AA) is to be confirmed. The UI follows its basic practices but has not been audited. | PH | Accessibility acceptance |
| OI-25 | Java version | The specification names Java 17 (OpenJDK 17). At the project owner's request the backend targets **Java 21 (LTS)**. Spring Boot 3.5 supports it, and code written for 17 runs unchanged. PhilHealth must approve this deviation, or the build can be switched back by setting `java.version` to 17 in `backend/pom.xml` and the base images in `backend/Dockerfile`. | PH | R-2.1 compliance |
| OI-26 | CMS approval policy | Content needs a second approver, except that Super Administrators may publish their own items (audited as `CONTENT_SELF_APPROVED`; switch off with `QMS_CMS_SUPER_ADMIN_SELF_APPROVAL=false`). PhilHealth to confirm whether self-approval by Super Administrators is acceptable. | PH | CMS acceptance |
| OI-27 | SLA targets and agent evaluation | The SLA values (national default: wait 30 min, process 15 min, 90% compliance) are placeholders, and the per-region values must come from PhilHealth (e.g. the Citizen's Charter processing times). PhilHealth must also confirm that the SLA status is decided on processing time only, with waiting compliance reported separately, and whether agent performance reports may be used for staff evaluation (HR and data-privacy implications). | PH | Agent performance acceptance |
